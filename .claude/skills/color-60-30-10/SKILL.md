# The 60-30-10 Color Rule, Applied Like a Designer

## What the rule actually is (and isn't)

60-30-10 is a proportion, not a palette. It says: roughly 60% of what the eye sees should be one dominant color, 30% a secondary color that supports it, and 10% an accent that draws the eye to what matters most. The number of colors it produces is the easy part — three roles, not necessarily three hexes, since each role is usually a small family (a base plus a couple of tints/shades for depth, hover states, and borders). The hard part, and the part that separates a professional result from a beginner one, is everything the ratio itself doesn't tell you: which three colors, mapped to which actual pixels, checked against which constraints. That's what this skill is for.

Three things a designer knows that a surface-level reading of the rule misses:

1. **The ratio describes visual weight, not literal pixel-counting.** A small, saturated accent patch can carry 10% of the *attention* while covering far less than 10% of the *area* — a bright button on a mostly-white page reads as "the accent color" even though it's a tiny fraction of the canvas. Don't chase the percentages with a ruler; chase the effect: one calm base the eye rests on, one supporting layer that adds structure, one color reserved almost entirely for the handful of things that most need attention.

2. **Semantic colors are not the accent color, and they don't share its budget.** Error red, success green, and warning amber mean something specific to users and need to stay reserved for that meaning — if the brand accent is also red, a destructive-action warning and an ordinary "click here" button become visually indistinguishable, which is a real usability failure, not just an aesthetic one. Semantic colors get their own small, consistent set, used only for their purpose, separate from whatever the 10% accent is doing elsewhere in the UI. See `references/ui-mapping.md`.

3. **The rule adapts to dark mode, it doesn't disappear in it.** The proportions hold — a dominant surface, a supporting layer, a sparing accent — but the specific values almost always need independent tuning rather than a mechanical invert, because saturated colors that read as vibrant accents on white frequently look harsh or vibrate uncomfortably on a dark background. See `references/ui-mapping.md` for how to adapt.

## Workflow

**1. Establish what's being colored.** A marketing landing page, a data-dense dashboard, a form-heavy app, and a slide deck all put different demands on the same rule — a dashboard already has color doing real work in its charts and status indicators, which changes how much room is left for a decorative accent. If a `dataviz`-style skill or reference is available for chart-series colors specifically, treat that as a separate concern that composes with this one rather than something this rule overrides: 60-30-10 governs the UI shell (backgrounds, chrome, navigation, primary actions), chart/data-series palettes are their own system layered on top of it.

**2. Establish the color inputs.** If the user gave a brand color, a reference image, or an existing palette, that's the seed — usually the dominant or the accent depending on how saturated it is (a bold, saturated brand color is much more often the 10% accent than the 60% dominant; a 60% color needs to be calm enough to sit behind everything else without fatiguing the eye). If nothing was given, ask what mood or brand feeling is intended before inventing colors from nothing — "clean and clinical" and "warm and approachable" produce very different dominant colors even at the same lightness. Read `references/palette-construction.md` for how to derive the full three-role palette (with tints/shades for each role) from a single seed color using real color theory rather than guessing.

**3. Map roles to actual regions.** Decide, concretely, which UI elements are dominant (page/app background, large surfaces), which are secondary (cards, panels, headers, borders, secondary buttons, dividers), and which are accent (primary CTA, active/selected states, key links, critical highlights) — plus the separate semantic set for status/feedback. `references/ui-mapping.md` has the standard mapping and where designers commonly get it wrong (most often: too many things fighting for accent status, which erases the hierarchy the whole rule exists to create).

**4. Verify contrast, not just taste.** Every text/background and icon/background pairing that resulted from steps 2-3 needs to actually meet WCAG contrast minimums (4.5:1 for normal text, 3:1 for large text and meaningful UI components) — a palette that looks balanced in a swatch strip can still produce illegible white-on-light-gray body text once applied. Check this before calling a palette finished, not after a user reports it's hard to read. `references/ui-mapping.md` has the specific thresholds and how to fix a pairing that fails without abandoning the palette.

**5. Build both modes if the surface supports dark mode.** Don't treat dark mode as an afterthought toggle — derive it deliberately using the adaptation guidance in `references/ui-mapping.md`, and re-check contrast for the dark pairing separately; a ratio that passes in light mode doesn't automatically pass once the background inverts.

**6. Apply it consistently, then check your own work.** Once the palette and mapping are decided, hold to them — introducing a one-off color for a single component is exactly the kind of drift that erodes the 60-30-10 balance over time. Before calling a build done, do a quick pass with `references/audit-checklist.md`: is any one region visually competing with the accent for attention, are semantic colors staying in their lane, does the result actually look like it has *one* clear dominant color rather than several colors of similar weight fighting for the eye.

## Auditing an existing design

Same checklist, run in reverse: look at the design (or its CSS/design tokens/theme file if working in code) and classify what's actually there before deciding what to change. The most common real-world violation isn't "wrong colors," it's **too many colors carrying equal visual weight** — a page with six different button colors, or a dashboard where every card has its own accent, has no dominant color at all even if any single element looks fine in isolation. `references/audit-checklist.md` walks through diagnosing this and consolidating back down to a working 60-30-10 structure without necessarily discarding the brand's existing colors — usually the fix is choosing which of the existing colors gets which role and demoting the rest to occasional use, not inventing a new palette from scratch.
